# LCA standards and interoperability profile

## Standardization principle

LCA should profile existing standards and define only the domain-specific semantics that existing standards do not cover. It should not attempt to make “consciousness continuity” a standards claim.

## Normative levels

- **MUST:** required for an LCA MVP-conforming implementation.
- **SHOULD:** expected for a serious pilot unless a documented reason exists not to use it.
- **MAY:** useful optional binding.
- **OPEN:** no mature standard currently resolves the LCA-specific question.

## Profile matrix

| Area | Standard/profile | MVP level | LCA use |
|---|---|---:|---|
| Record validation | JSON Schema Draft 2020-12 | MUST | validate the canonical JSON envelope and per-type records |
| Time | RFC 3339 / ISO 8601-compatible UTC timestamps | MUST | observed, recorded, valid-from, superseded, and review times |
| Deterministic hashing input | RFC 8785 JSON Canonicalization Scheme | SHOULD | canonicalize record/event JSON before hashing or signing |
| Provenance | W3C PROV-DM / PROV-O | SHOULD | map source records, transformations, activities, agents, and derivations |
| Rights and permissions | W3C ODRL 2.2 | SHOULD | express permission, prohibition, duty, purpose, constraint, and party |
| Signed claims | W3C Verifiable Credentials Data Model 2.0 and Data Integrity 1.0 | MAY for MVP; SHOULD for pilot | sign SourceReviews, AuthorityGrants, steward attestations, and recovery manifests |
| AI governance | NIST AI RMF 1.0 plus Generative AI Profile | SHOULD | govern, map, measure, and manage ML risks and evaluation evidence |
| Runtime observability | OpenTelemetry traces, metrics, and logs | SHOULD | correlate ingestion, retrieval, model runs, policy decisions, and failures |
| Authentication | OIDC/OAuth 2.0 or local equivalent | SHOULD for multi-user pilot | authenticate source, steward, reviewer, and service identities |
| Cryptographic signatures | Ed25519 or another approved signature profile | MAY for local MVP; SHOULD for shared pilot | sign events, grants, exports, and recovery packages |
| Software/model inventory | SPDX or CycloneDX SBOM plus model card/dataset card | SHOULD | record code, dependency, model, and dataset provenance |
| Accessibility | WCAG 2.2 AA for review interface | SHOULD | ensure source review and rights workflows are accessible |
| Personal-data governance | jurisdiction-specific privacy/legal controls | MUST for real personal data | consent, purpose, retention, deletion, third-party rights, and export controls |
| Identity continuity semantics | no external standard | OPEN | LCA defines Archive/Portrait/Bud/Branch and P/C/F/A as a domain profile |

## Recommended LCA binding

### JSON Schema

Use Draft 2020-12 as the validation boundary. JSON Schema is appropriate for the machine-readable envelope, but it should not be mistaken for a complete ontology. Relationship semantics, provenance meaning, rights policy, and lifecycle transitions need additional profile documents and tests.

### PROV mapping

Map the LCA model approximately as follows:

| LCA concept | PROV concept |
|---|---|
| SourceRecord, Episode, Claim, Interpretation | `prov:Entity` |
| Transformation, model run, ingestion, review | `prov:Activity` |
| living source, assistant/model, steward, reviewer | `prov:Agent` |
| derived from | `prov:wasDerivedFrom` |
| generated by transformation | `prov:wasGeneratedBy` |
| attributed to source/person/model | `prov:wasAttributedTo` |
| used evidence | `prov:used` |
| review/endorsement responsibility | `prov:wasAssociatedWith` and qualified relations |

LCA-specific fields such as response class, weather privacy, authority scope, invariant fidelity, and lifecycle state remain extensions.

### ODRL mapping

Represent `AuthorityGrant` as a rights policy with:

- asset: target object or scope;
- party: source, steward, portrait, bud, branch, reviewer, or service;
- action: quote, infer, retrieve, train, export, modify, sign, delegate;
- constraint: purpose, domain, privacy tier, time, jurisdiction, or review status;
- duty: logging, attribution, disclosure, human review, or revocation handling;
- prohibition: prohibited action such as source modification or private-weather access.

ODRL is an expression language, not an enforcement engine. LCA still needs a policy evaluator and audit trail.

### Verifiable Credentials/Data Integrity

Use signed credentials selectively. Appropriate claims include:

- “this SourceReview was issued by the authenticated living source”;
- “this AuthorityGrant was issued by the named steward”;
- “this recovery manifest corresponds to this canonical snapshot”;
- “this model run was evaluated against this dataset snapshot.”

Do not issue a verifiable credential asserting that a Portrait is the person. A cryptographically signed claim can prove who issued a statement and whether it was altered; it cannot prove subjective continuity.

### NIST AI RMF

Use the AI RMF functions as the ML operations spine:

```text
GOVERN -> roles, rights, consent, model change, incident handling
MAP    -> sources, harms, affected parties, scope, context, failure modes
MEASURE-> evidence, retrieval, authorship, privacy, drift, recovery metrics
MANAGE -> mitigations, review queues, rollback, exclusion, escalation
```

Pin the implementation to a named AI RMF version because NIST notes that the framework is being revised. Record the profile version in the LCA governance manifest.

### OpenTelemetry

Use OpenTelemetry for runtime traces and metrics, not as the canonical LCA event ledger. The LCA ledger answers what authoritative state changed and why. OpenTelemetry answers how the service executed, how long it took, and where an operational failure occurred. Link them through `trace_id`, `span_id`, `event_id`, and `model_run_id`.

## Standards not sufficient by themselves

Existing standards do not solve:

- source versus assistant authorship in a mixed dialogue;
- the meaning of “good inference, not explicitly said”;
- the Archive/Portrait/Bud/Branch lifecycle;
- P/C/F/A orientation transitions;
- invariant fidelity;
- weather as context without diagnosis;
- cognitive-lineage succession and the right not to continue;
- the distinction between a signed claim and an identity claim.

These require LCA-specific schemas, policy rules, test fixtures, and human governance.

## Conformance profiles

### LCA-Core-0.1

MUST include:

- JSON Schema validation;
- stable IDs;
- RFC 3339 timestamps;
- immutable versions;
- append-only event ledger;
- provenance and authorship fields;
- lifecycle and validation states;
- evidence IDs on generated responses;
- authority decision record;
- recovery export;
- conformance tests.

### LCA-Governed-0.1

LCA-Core plus:

- W3C PROV mapping;
- ODRL-compatible rights expressions;
- authenticated SourceReview and AuthorityGrant;
- privacy-tier enforcement across retrieval/index/training/export;
- model and dataset registry;
- AI RMF risk/evaluation record;
- audit and rollback operations.

### LCA-Research-0.1

LCA-Governed plus:

- longitudinal Bud protocol;
- independent review;
- preregistered continuity experiments;
- neural-observation source-class experiments if ethically approved;
- explicit separation of behavioral continuity from subjective continuity claims.
